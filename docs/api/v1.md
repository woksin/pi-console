# Daemon API v1

The primarily read-only API of the M1 console daemon (`packages/daemon`). It is v0 ([v0.md](v0.md)) plus additive
definitions; everything v0 says about representations, pagination and SSE still holds unless this page says
otherwise. The testkit mock daemon serves the same v1 routes for UI work.

The daemon serves the API with plain `node:http`, not Arc ([ADR-0010](../adr/0010-daemon-http-plain-node-fallback.md)).

```sh
pi-console daemon --port 4777 --web-dist packages/web/dist
TOKEN=$(cat ~/.pi-console/token)
curl -H "Authorization: Bearer $TOKEN" http://127.0.0.1:4777/api/v1/overview
curl -N -H "Authorization: Bearer $TOKEN" http://127.0.0.1:4777/api/v1/stream
```

## Optional native memory review (`/memory-actions`)

`GET /memory-actions/availability` uses normal read authentication and returns `MemoryActionAvailability`:
`version: 1`, `available`, nullable provider `generation`, and `reason` (`available`, `disabled`, `unavailable`).
Disabled, missing and disconnected providers stay unavailable; there is no offline queue.

`POST /memory-actions` requires the separate memory-control credential, exact same-Origin, and
`x-pi-console-csrf: 1` (including bearer requests). JSON is exactly `MemoryActionRequest`:
`{requestId, itemId, action: 'confirm' | 'reject'}`. IDs are 1–128 ASCII letters/digits/underscore/hyphen.
No text, target, expiry, actor or human-proof fields are accepted. The daemon resolves the single eligible live
native session and persists `MemoryActionReceipt` before delivery. HTTP 202 is intent, **not approval**.

`GET /memory-actions/:requestId` requires the same control credential and returns its durable receipt.
Identical retries return the original receipt without delivery; changed payloads or credential reuse get 409.
Receipts include request/item/action, resolved `sessionId`, provider `generation`, `connectionGeneration`,
hashed `tokenId`, millisecond `createdAt`/`expiresAt`/`updatedAt`, `state`, nullable source `reason` and `eventId`.
States: `awaiting-human`, `awaiting-ingestion`, `observed-applied`, `declined`, `conflict`, `unavailable`, `expired`, `unknown`.
Only matching canonical source ingestion produces `observed-applied`. Disconnect/restart never redispatches.
Review intent expires after 90 seconds, cancelling the native prompt best-effort. An unverified claimed write
becomes unknown after 30 additional seconds and may reconcile on later ingestion.

Limits: 1 KiB request bodies, 16 KiB frames, 32 live connections, 32 frames/second/connection,
six new requests/minute/control-token and session, one awaiting-human review/session, 10,000 durable receipts
(hard fail-closed capacity, never evict-and-replay). Malformed intent: 400; missing item/receipt: 404;
unavailable/busy/not-proposed/conflicting id: 409; missing scope/Origin/CSRF: 403; rate/capacity: 429.
No error or source result claim implies a memory mutation. These routes are daemon-only, not mock interventions.

## Configuration

`pi-console daemon [--data-dir <dir>] [--port <n>] [--web-dist <dir>] [--sessions <dir>]... [--backfill-days <n>]`

Defaults first, then `<data-dir>/config.json` (`port`, `webDist`, `sessionRoots`, `backfillWindowDays`, optional `memoryActions: true`; relative
paths resolve against the data directory), then flags. The data directory (default `~/.pi-console`) holds `token`,
`console.db` (event log and projection snapshots, ADR-0001) and `config.json`. The bind address is not
configurable: the daemon listens on `127.0.0.1` only.

## Security

Implements [ADR-0006](../adr/0006-security-model.md) and [security.md](../security.md) for a read-only daemon.

- **Bind**: `127.0.0.1` only.
- **Token**: 256 random bits, hex, in `<data-dir>/token`. The directory is forced to `0700` and the file to `0600`;
  a symlinked or foreign-owned token file is refused. The process keeps only a SHA-256 hash and compares in
  constant time. The default M1 scope is `read`; optional memory review uses a separate credential (see above). Rotation: stop the daemon, delete the file, start again. The token
  is never logged or printed.
- **Every request**: `Host` must be `127.0.0.1:<port>` or `localhost:<port>` (DNS rebinding). An `Origin`, when
  present, must be `http://` plus one of those. `Sec-Fetch-Site: cross-site` is refused. Failures are `403`.
- **API**: `Authorization: Bearer <token>`, or the browser cookie below. Missing or wrong credentials are `401`.
- **Browser bootstrap**: `GET <any path>?token=<token>` answers `303` to the same URL without `token` and sets
  `piConsoleToken` with `HttpOnly; SameSite=Strict; Path=/api/v1`. A wrong token is `401`.
- **Cookie limits**: the cookie opens `/api/v1/stream` only with an allowed `Origin`, so a context that sends no
  Origin cannot use it to open a stream. Mutating methods with the cookie would also need `X-Pi-Console-Csrf: 1`
  and an `Origin`; M1 has no mutating routes, every non-GET API request is `405`.
- **Headers on every response**: `Cache-Control: no-store`, `X-Content-Type-Options: nosniff`,
  `Referrer-Policy: no-referrer`, `Cross-Origin-Resource-Policy: same-origin`, `X-Frame-Options: DENY`. API bodies
  carry `Content-Security-Policy: default-src 'none'; frame-ancestors 'none'; base-uri 'none'; form-action 'none'`.
- **Output**: every string in every JSON body and SSE frame passes through the adapters' secret scanner again and
  loses C0/C1 control characters (except tab and newline) and bidirectional overrides. Ingestion already redacts;
  this is the last line of defence, specified by `packages/daemon/src/secrets.test.ts`.
- **Limits**: 16 KiB of headers, 10 s request timeout, transcript `limit` at most 1000.

## Static web bundle

Paths outside `/api/` serve the configured web bundle (`--web-dist`). No token is needed for static files; the Host
and Origin checks still apply. Extensionless paths that are not files fall back to `index.html` (client routes).
`..` segments, NUL bytes, backslashes and malformed escapes are `400`; symlinks that resolve outside the bundle are
`404`. A missing or unconfigured bundle is a plain-text `404`; the API keeps working. Pages carry:

```text
default-src 'none'; script-src 'self'; style-src 'self'; img-src 'self' data:; font-src 'self'; connect-src 'self';
manifest-src 'self'; base-uri 'none'; form-action 'none'; frame-ancestors 'none'; object-src 'none'
```

The web bundle therefore has no inline scripts or styles.

## HTTP queries

All paths have prefix `/api/v1`. Successful GETs are `200` with the named `$defs` entry from
[`schemas/api.json`](schemas/api.json); errors are `{error}` (`error`) with `400`, `401`, `403`, `404` or `405`.

| Method/path | Response `$defs` | Notes |
| --- | --- | --- |
| GET `/overview` | `overview` | As v0 |
| GET `/sessions` | `sessions` | As v0 |
| GET `/sessions/:id` | `sessionDetail` | Unknown id `404` |
| GET `/sessions/:id/transcript?after=0&limit=100` | `transcript` | As v0 |
| GET `/sessions/:id/transcript?around=<entryId>&limit=100` | `transcript` | Window centred on the entry; unknown entry `404` |
| GET `/requests?filter=all\|unanswered\|interrupted` | `requests` | Other filters `400` |
| GET `/questions`, `/messages`, `/jobs` | `questions`, `messages`, `jobs` | As v0 |
| GET `/resets` | `resets` | Reset history; supports the same opt-in paging |
| GET `/memory-items` | `memoryItems`, `memoryItemPage` | Read-only intent-memory items; paging as below, plus `status=active\|proposed\|done\|superseded\|withdrawn\|rejected` (anything else `400`). A `proposed` item carries `command`, the exact `/memory confirm <id>` text a human runs in an interactive pi session; `/memory reject <id>` is its counterpart. The console shows it and never runs it |
| GET `/sessions/:id/memory` | `sessionMemory` | Per-session counts by status, `proposedConfirmable`, `unresolved` and the newest five handoffs' memory figures; unknown id `404` |
| GET `/needs-you` | `needsYou` | Ranked attention items. `reason` also includes `proposed-memory` (additive: one item per session with recorded-proposed memory items, `memory:unlinked` for those without a session) |
| GET `/graph` | `graph` | Lane nodes and aggregated lane edges; no layout data. Lanes are served here, not by a separate route |
| GET `/health` | `health` | See below |
| GET `/settings` | `settings` | Read-only settings without paths or credentials; `sources` lists every source (`session-jsonl`, `context-budget`, `lane-messages`, `lane-heartbeats`, `question-store`, `issue-work`, `intent-memory`, `phase-ledger`) with `enabled` |
| GET `/stream` | `event` | SSE, see below |

Each `/health` source entry also carries `errors` (files that failed in the last poll; no text, no paths).

`/health` reports `status` (`starting` until the first ingestion pass over the backfill window, then `ok`), the
event log's last sequence number and database size (with WAL), the projection position, queue depth (log events
not yet projected plus events waiting for delta mapping) and skipped events, the stream id, client count and
retained deltas, per-source file count, unread bytes and last poll time, backfill state and process memory.
`eventLoop` contains `p50`, `p99` and `max` event-loop delays in milliseconds, sampled at 5 ms resolution
since the daemon started listening. Reads do not reset the histogram; before the first sample all three are zero.

### Intent memory (read-only)

The daemon reads the producer's store (`events.jsonl`, `journal/*.jsonl`) without locking or writing and never confirms,
rejects or retires anything: `command` is text for a human. Item statuses are the producer's where the store says so
(`statusBasis: recorded`: orders, decisions, items without authority, items from a non-human message, confirms and retires)
and an assumption where the producer's rule engine decides (`assumed`, shown as such). The console never keeps journal
message text, so `unresolved.lowerBound` counts human messages that no classification and no item cites; the exact figure is the
producer's, and `atLastHandoff` is read from the newest handoff file that has memory figures. Handoff files are read on demand,
never ingested: an absolute `.ai-work/handoffs/<name>.md` path that passes the denylist, is a regular non-symlink file of at most
256 KiB, and yields only integers; any failure gives null figures. `events.jsonl` has no rotation, so a very large store makes the
first read long.

### Paging

`GET /api/v1/{sessions,requests,questions,messages,jobs,resets,memory-items}` without `limit` returns the complete `{items}` exactly as
before. With `limit` (1 to 1000) it returns `{items, nextCursor, hasMore, total}`: a keyset page over the list's
total order (timestamp, then id), so concurrent upserts never skip or repeat a row. `order=desc` is the exact reverse
(default `asc`); `after` is the opaque `nextCursor` of the previous page, and one minted for another collection or
malformed is 400, as are a bad `limit` or `order`. `sessionId` narrows requests, questions, messages (either end), jobs and resets to
one session; `total` counts the narrowed list. `requests` also takes `filter`. Resets are ordered by `(at, id)`; memory items by the `at` of their add event, then id. A memory item's session is its `session` scope, else the session of the message it cites; items with neither (`sessionId` null) are in no session's filter.

## SSE

Frames, event names, payloads, the 10,000-delta ring, heartbeats and the 1 MiB slow-consumer limit are as in v0.
Differences:

- **Ids identify stream frames, not log events.** Every published update consumes one consecutive numeric id,
  even when one log event produces multiple updates. Both implementations replay individual frames: resuming
  after an entity frame delivers the remaining session frames without a gap or duplicate. Snapshots use the
  current stream position; keep-alives consume no ids.
- **Ids survive restarts.** The daemon persists the stream high-water mark before publishing and reserves a
  newer snapshot position on restart. The replay ring is in memory, so every pre-restart id gets a fresh
  `snapshot`, including the last id before shutdown. An id equal to the current position gets only new deltas.
- **Coalescing.** Log events applied in the same tick are grouped; each touched entity is sent once, as its state
  after the group, in first-touched order. Ids stay contiguous while observed. With no connected clients the daemon
  may omit delta queries and reserve a new stream position instead; it clears the replay ring so a resume from
  before that gap gets a fresh snapshot, never incomplete history. Request/answer events retain their
  `request.observed`/`request.interrupted` upserts; question lifecycle events retain `question.asked` upserts,
  never snapshots. A batch additionally emits one `session.updated` per session whose derived status or
  needs-you items changed, comparing before/after batch state (including both owners of reassigned entities).
  Repeated changes expose only final entity state and net derived changes. The mock uses the same entity-plus-
  session encoding. API v1 has no overview/needs-you SSE event: clients invalidate/refetch those endpoints on
  request, question and session upserts; overview status counts can also be derived from updated sessions.
- Snapshot payloads are built from the read models at connection time and are a bounded screen state: every active
  item (running job, unanswered or possibly-unseen request, open question, unread message, non-idle session, and
  anything the needs-you list points at) plus the newest 200 of each collection, ascending in the usual list order.
  `totals` gives the full size of each collection and `bounded` names the collections that only hold a window; an
  absent `bounded` means every list is complete. Sessions are kept whole up to 500; beyond that they are windowed too,
  always with the sessions that own kept items and every parent of a kept session. Resets contain only the newest 200
  belonging to kept sessions, ordered by descending `(at, id)`; active-only snapshots carry no resets. `totals.resets`
  counts all resets and `bounded` includes `resets` whenever any were omitted. Complete reset history is available through
  paged `GET /resets` or the existing `GET /sessions/:id` detail used by both clients.
  A snapshot above half the slow-client cap (1 MiB) degrades to active items only. If that frame still exceeds the full
  cap, an empty minimal snapshot retains full totals and marks every pageable collection bounded. The daemon warns once
  with the frame sizes; history remains reachable through pages and per-session detail. No snapshot larger than the cap
  is written. A cap too small even for the minimal envelope is rejected with HTTP 503 before SSE headers are sent.
  Clients merge a bounded snapshot by id, keep history pages they already loaded, and drop rows that were active but are
  no longer in the snapshot.

## Conformance

`packages/testkit/src/conformance/daemon-conformance.ts` is one suite for every daemon: read routes and schemas,
the security boundary, SSE snapshot, contiguous deltas and resume. It runs against the mock
(`packages/testkit/src/mock-daemon/conformance.test.ts`) and the real daemon (`packages/daemon/src/conformance.test.ts`).

## Startup

Measured by `npm run gate:integration -- --scope daemon` (`packages/daemon/src/startup.integration.ts`): time from
start until `/api/v1/overview` answers, with 100,000 synthetic events in the log. On an Apple-silicon laptop
(2026-11-20, Node 26): cold start (projecting the whole log) about 1.4 s, warm start (projection snapshots) about
5 ms. The log is fully projected before the port opens, so the first response is never partial; session ingestion
runs after the port opens.

## Known limitations (M1)

These follow from the events that exist; the daemon does not invent events to hide them.

- **Lanes and branches**: the M1 catalogue does not link sessions to lanes or branches, so every session reports
  lane `unassigned` and branch `''`. A job or question without a known session belongs to `console`.
- **Graph**: lane nodes come from lane events; edges come from messages (`message`) and lane status naming another
  lane (`waiting-on`, `barred-by`). No `spawn` edges: they need a session-to-lane link.
- **Transcripts**: the transcript reader belongs to the P2 adapters and is not there yet. The daemon has a
  `TranscriptReader` seam (`packages/daemon/src/api/transcripts.ts`) and serves empty pages until it lands;
  `around` is `404` for every entry.
- **Sources**: only pi session JSONL files are ingested in M1.
